# Java CompletableFuture — лабораторная

## Цель

На коде понять, как `CompletableFuture` помогает backend-приложению запускать независимые операции одновременно, собирать их результаты, обрабатывать ошибки и не терять контроль над CPU-bound вычислениями.

## Карта понятий

```text
Несколько независимых операций
        │ CompletableFuture запускает работу
        ▼
Executor / common pool
        │ результаты становятся готовы
        ▼
thenCombine / allOf собирают продолжение
```

- **CompletableFuture** — контейнер для результата, который появится позже, и цепочки действий после него.
- **Executor** — компонент, который решает, на каких потоках выполнять асинхронную работу.
- **common pool** — общий `ForkJoinPool`, который `supplyAsync(...)` использует без явного executor.
- **Composition** — сборка нескольких futures в один сценарий через `thenCombine`, `thenCompose` или `allOf`.
- **join()** — ожидание результата; при ошибке выбрасывает unchecked `CompletionException`.
- **CPU-bound** — задача, где время тратится на вычисления, а не на ожидание внешнего ресурса.

## 1. Два независимых запроса и `thenCombine`

**Код:** [`Lab_Main.java`](../src/main/java/org/Lab_Main.java). Один искусственный запрос ждёт 500 мс, второй — 700 мс.

| Способ | Ожидаемое время | Почему |
| --- | --- | --- |
| Последовательно | около 1,2 секунды | Второй запрос стартует после первого |
| `supplyAsync` + `thenCombine` | около 0,7 секунды | Оба ожидания перекрываются; нужен самый долгий путь |

`supplyAsync` возвращает future сразу. `thenCombine` не блокирует вызывающий поток: он только описывает, что сделать, когда готовы оба результата. Реальное ожидание в этом маленьком консольном примере находится в конце — в `join()`.

### Мои выводы

> Независимые операции можно запускать вместе, а не выстраивать в очередь.

> `thenCombine` собирает два результата только тогда, когда готовы оба.

> `join()` лучше оставлять на границе сценария, а не ставить после каждого шага.

## 2. Цепочка стадий и executor

**Код:** [`ThreadOutput_Main.java`](../src/main/java/org/ThreadOutput_Main.java)

В опыте 12 задач создаются через `supplyAsync(..., executor)` с fixed pool из трёх потоков. Затем каждая проходит `thenApply` и `thenAccept`.

Пример наблюдения:

```text
Task 00: load    — Thread[#21,pool-1-thread-1,5,main]
Task 00: convert — Thread[#21,pool-1-thread-1,5,main]
Task 00: result  — DATA-0
```

`thenApply` без суффикса `Async` часто исполняется тем потоком, который завершил предыдущую стадию. Это удобно для короткого преобразования. Если продолжение долгое или блокирующее, его нужно явно вынести в подходящий executor через `thenApplyAsync(..., executor)`.

### Мои выводы

> Future описывает цепочку работы, но поток выбирает executor.

> Обычная стадия продолжает работу там, где завершилась предыдущая.

> Долгое продолжение нельзя незаметно класть в общий пул.

## 3. Настоящий HTTP без блокирующего `send`

**Код:** [`BlockingHttp_Main.java`](../src/main/java/org/BlockingHttp_Main.java)

20 запросов запускаются через `HttpClient.sendAsync(...)` к endpoint с задержкой в одну секунду. Каждый запрос возвращает `CompletableFuture<HttpResponse<Void>>`; `allOf` ждёт завершения всех futures.

| Параметр | Что проверить при запуске |
| --- | --- |
| Задач | 20 |
| Ответов | 20; статус каждого напечатан отдельно |
| Общее время | Обычно ближе к одной задержке, но зависит от сети и сервера |

`sendAsync` не удерживает вызывающий поток, пока сеть ждёт ответ. Но future всё равно нужно завершить: в опыте это делает `allOf(...).join()`. `exceptionally` переводит ошибку отдельного запроса в понятный вывод, поэтому один сетевой сбой не отменяет наблюдение за остальными.

Порядок печати задач определяется получением ответов, а не их номерами. DNS, TCP/TLS, лимиты удалённого сервера и сеть делают результат нестрогим benchmark.

### Мои выводы

> Асинхронный HTTP возвращает управление сразу, а результат приходит в future.

> `allOf` собирает завершение многих операций, но сам не собирает их значения.

## 4. Ошибка как часть цепочки

**Код:** [`BlockingHttp_Main.java`](../src/main/java/org/BlockingHttp_Main.java)

У future есть два нормальных пути: значение или исключение. В примере `exceptionally` получает исключение сетевого запроса, печатает его и возвращает `null`, чтобы соответствующая ветка стала успешно завершённой для `allOf`.

| Оператор | Когда использовать |
| --- | --- |
| `exceptionally` | Нужен запасной результат только при ошибке |
| `handle` | Нужно обработать и значение, и ошибку |
| `whenComplete` | Нужен лог или метрика без изменения результата |

Не стоит скрывать ошибку автоматически в production-коде. Здесь это осознанная часть эксперимента: все 20 HTTP-веток доходят до финального `allOf`, а в консоли остаётся причина сбоя.

### Мои выводы

> Ошибка future тоже проходит по цепочке и должна быть спроектирована.

> Обработчик ошибки должен либо дать понятный fallback, либо сохранить ошибку для вызывающего кода.

## 5. CPU-bound: `CompletableFuture` не добавляет ядер

**Код:** [`CpuBoundMain.java`](../src/main/java/org/CpuBoundMain.java)

80 задач считают простые числа до `300_000`. Сначала работа идёт через fixed executor размером в число доступных процессоров, затем через common pool по умолчанию.

| Вариант | Что сравнивать | Почему |
| --- | --- | --- |
| Fixed executor | Время и предсказуемость | Размер параллелизма задан явно |
| Common pool | Время и влияние на другую работу | Пул общий для `CompletableFuture` без executor |

Обе версии распараллеливают CPU-работу лишь до доступных ядер. Много futures не означают столько же одновременно выполняющихся вычислений. Один запуск не является честным benchmark: JIT, прогрев и параллельная активность машины заметно влияют на цифры.

### Мои выводы

> `CompletableFuture` композирует асинхронность, а не создаёт дополнительные CPU.

> Для тяжёлой CPU-работы нужен ограниченный, явно выбранный executor.

> common pool удобен для коротких задач, но его не стоит занимать долгими или блокирующими операциями.

## Практическое правило

| Ситуация | Подход |
| --- | --- |
| Несколько независимых запросов | Запустить futures вместе и собрать через `thenCombine` или `allOf` |
| Следующий шаг зависит от предыдущего результата | Использовать `thenCompose`, не делать преждевременный `join()` |
| Ошибка внешнего вызова | Явно выбрать `exceptionally`, `handle` или передачу ошибки выше |
| Тяжёлые CPU-вычисления | Передать ограниченный executor; не полагаться неявно на common pool |

## Следующий эксперимент

1. В `Lab_Main` заменить один `supplyAsync` на зависимый `thenCompose` и сравнить критический путь.
2. В `BlockingHttp_Main` временно указать неверный URL и посмотреть, как `exceptionally` меняет поведение `allOf`.
3. Затем сделать backend mini-task: параллельно загрузить профиль, права и заказы, собрать dashboard и передать CPU-обработку в отдельный ограниченный executor.
